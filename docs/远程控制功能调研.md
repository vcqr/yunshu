# 远程控制(局域网点对点)功能调研

> 调研日期:2026-10-27。结论:**可行,建议做**。传输层三大件(UDP 发现、Noise 加密直连、TOFU 信任)已具备,真正新做的是受控端「屏幕采集 + 输入注入」、控制端「画面渲染 + 事件发送」、以及 ID+密码 认证与无人值守机制,均有成熟 Rust 生态支撑,无卡点。

## 一、需求范围

- 局域网点对点,不经过任何服务器(与云书现有定位一致)
- 在飞鸽主机列表点击对方发起控制;输入对方的 **机器 ID + 密码**(随机 / 固定 / 一次性三种模式)
- 支持**无人值守**:对方无需人在电脑前,凭固定密码直接受控
- 支持**反向协助请求**:我发起"请求对方协助",对方同意后直接建连受控,无需手动输密码

## 二、现有代码能直接复用什么

| 现有能力 | 位置 | 远程控制怎么用 |
|---|---|---|
| UDP 广播发现 `{id, name, port}` | `crates/yunshu-core/src/pigeon.rs:396`(Announce)、`server.rs:63`(发现表) | 主机列表直接用,点主机发起控制 |
| Noise XX 加密直连 + WS | `pigeon.rs:454`(`pigeon_connect`) | 新开一条专用 `/remote-ws`,独立 Noise 会话 |
| TOFU 指纹固定 | `pigeon.rs:84`(known_peers.json) | **机器 ID 直接取指纹前 8 位 hex**,零新增基础设施 |
| 信任确认 / 防打扰 / 握手抑制 | `pigeon.rs:516`、`dnd_skipped` | 密码错误锁定直接复用此思路 |
| CoreEvent / UiRequest 事件桥 | `crates/yunshu-core/src/lib.rs:113`、`lib.rs:149` | 新增一组事件/请求枚举即可透传到前端 |
| arboard 剪贴板 | yunshu-core 依赖 | 控制中剪贴板同步是免费赠品 |
| pigeonbot 无头测试节点 | crates/pigeonbot | 扩展协议层 e2e(认证流程用假帧源测试) |

### 两个现状问题,需一并处理

1. **`self_id` 每次启动随机**(`server.rs:206`),而"输入对方机器 ID"需要稳定身份。
   方案:用静态密钥(`pigeon_key.bin`,已持久化)指纹前 8 位 hex 作公开机器 ID(16⁸≈43 亿,局域网无碰撞之忧),加入 UDP 广播包。输入 ID 即可从发现表定位 ip:port。
2. **不能复用飞鸽那条 WS 传视频**:现有加密泵是单链路 64 容量队列(`pigeon.rs:569`),大文件推送会把视频帧挤死。
   方案:远程控制走**独立连接**(同端口新路径 `/remote-ws`,独立 Noise 会话),顺带天然支持"控制一台还没建飞鸽链路的机器"。

## 三、总体架构

```
控制端(观看/操作)                        受控端(被看/被操作)
┌──────────────┐   Noise WS /remote-ws   ┌───────────────────┐
│ 观看窗口      │ ←── 视频帧('V' 前缀) ── │ 采集循环:截屏→编码  │
│ (Tauri 新窗口 │ ──── 输入事件 JSON ───→ │ enigo 注入键鼠      │
│  canvas 渲染) │ ←── 剪贴板/状态      ──→ │ arboard 同步剪贴板  │
└──────────────┘                         └───────────────────┘
```

- 受控端在现有 axum 上新增 `/remote-ws` 路由;连接后先 Noise XX 握手(复用 `new_handshake`),再走认证,通过后进入会话循环。
- 帧复用飞鸽的明文前缀方案:`'C'` 控制 JSON / `'F'` 文件块,新增 `'V'` 视频帧。
- 剪贴板同步双向:受控端剪贴板变化 → 推给控制端;控制端复制 → 注入受控端(arboard 已有)。

### 认证:三种密码模式(对齐 RustDesk / ToDesk 习惯)

| 模式 | 生命周期 | 存储 |
|---|---|---|
| 临时密码 | 启动时生成 6 位数字,托盘 UI 展示,重启可换 | 内存 |
| 固定密码 | 设置里配置,长期有效 | config.toml(加盐哈希,argon2/pbkdf2) |
| 一次性密码 | 反向协助时现场生成,仅本会话有效,用后即焚 | 内存 |

关键授权语义:**密码正确 = 授权完成**,不走指纹确认弹窗(否则无人值守无从谈起)。未信任设备靠密码把关;Noise XX 每会话密钥不同、天然防重放,密码直接在加密通道内传输即可。密码错误按防爆破策略处理(连续 5 次锁 10 分钟,复用 `dnd_skipped` 模式)。

### 无人值守

- MVP = 现有开机自启(登录后托盘常驻)+ 固定密码 + 密码正确即自动受控。
- 登录前可连(UAC 可见、锁屏可操作)需要系统服务(SYSTEM/daemon),放三期。

### 反向协助

与主动控制共用同一套协议,只是密码生成时序不同:

1. A 在列表点「请求协助」→ 经飞鸽链路发 `AssistRequest`
2. B 弹窗「A 请求控制你的电脑,允许?」→ 同意
3. B 现场生成一次性密码,本地进入受控待连状态,密码经飞鸽链路回传 A
4. A 用 B 的机器 ID + 一次性密码发起控制连接(`/remote-ws` 新建连)

### 协议消息(新增一族 RemoteWire,风格对齐 PigeonWire)

- 认证:`AuthRequest{mode, password}` → `AuthResult{ok, reason}`
- 会话:`Frame{seq, data}`(视频帧)、`InputEvent{mouse/keyboard/wheel}`、`ClipboardSync{text}`、画质/分辨率协商、`SessionEnd{reason}`
- 受控端能力协商:显示器列表、支持的编码格式、屏幕尺寸/DPI

## 四、编码与渲染(分两期)

- **一期:JPEG 帧流**。BGRA 截屏 → 缩放 → `jpeg-encoder`(纯 Rust)q75。1080p 约 150-250KB/帧,15-30fps ≈ 25-60 Mbps,局域网轻松扛住,端到端延迟约 20-50ms。前端 canvas/`<img>` 直接渲染,**零解码成本**。
- **二期:H.264 硬编**(MediaFoundation / VideoToolbox,VAAPI 可选)+ 前端 **WebCodecs** 解码(WebView2 与 macOS 13+ WKWebView 均支持)。带宽降到 5-15 Mbps,画质帧率双升。把「帧编码器」抽象成 trait,一期实现不堵路。
- 附带福利:JPEG 流天然兼容手机浏览器(MJPEG 思路),二期可白送手机端「只看不控」。

## 六、平台权限矩阵(本项目最大的坑,提前亮牌)

| 平台 | 采集 | 输入注入 | 无人值守 | 备注 |
|---|---|---|---|---|
| **Windows** | 无需权限 | 无需(SendInput) | 登录后可用(现有 autostart) | 用户态看不到 UAC 弹窗/锁屏/安全桌面,需明确告知"一期覆盖登录后场景";操作提权窗口亦不可行 |
| **macOS** | **屏幕录制 TCC** | **辅助功能 TCC** | 登录项 + 一次性授权即可 | ① 开发期 ad-hoc 签名**每次重编译授权即失效**(TCC 记签名),调试体验差;② 正式分发需 Developer ID 签名 + 公证;③ macOS 15 Sequoia 对屏幕录制授权有**周期性重确认**,对无人值守是持续打扰 |
| **Linux X11** | 无需 | 无需(XTEST) | systemd user 服务 | — |
| **Linux Wayland** | portal 弹窗授权 | 需 root/udev 规则 | 基本不可行 | 一期不支持,检测到 Wayland 明确提示走 X11 |

## 七、分期计划

- **一期 MVP**(估 1.5~2 周量级):
  Windows + macOS;JPEG 流 15-30fps;enigo 输入;机器 ID(指纹前缀)+ 临时/固定密码;反向协助(同意 → 一次性密码 → 直连);无人值守 = 自启 + 固定密码;观看窗口(Tauri 新窗口,canvas 渲染 + 键鼠捕获);受控端「正在被控制」醒目指示(托盘变红 + 一键断开,安全上必须有);剪贴板同步放尾巴。
- **二期**:H.264 硬编 + WebCodecs 解码;多显示器选择;画质自适应(按 RTT/丢帧调 JPEG 质量与帧率);Linux X11;手机浏览器「只看不控」。
- **三期**:Windows 服务化(免登录、UAC 可见)、macOS LaunchDaemon、文件回传(控制端向受控端传文件)。

新增代码量预估:core 侧 remote 模块 + 协议 ~2000 行;平台采集/注入(借 xcap/enigo)~500 行;前端观看窗口 + 弹窗 + 设置 ~1200 行;合计 3~4k 行。

## 八、风险清单

1. **macOS TCC**:开发期反复授权(换正式签名可解);Sequoia 周期性重确认对无人值守有打扰。
2. **链路竞争**:视频流与文件传输抢链路 → 已用独立 `/remote-ws` 连接规避(设计前置条件)。
3. **HiDPI / 多屏**:坐标映射与 DPI 缩放(Retina 采集分辨率是逻辑像素 2 倍);一期只控主屏,多屏做「显示器选择」放二期。
4. **密码爆破**:错误 5 次锁 10 分钟(IP 维度,复用 dnd_skipped 模式);密码哈希加盐存储。
5. **受控端知情权**:被控制时必须有醒目持续指示 + 一键断开,防止静默监视为恶意用途留口。
6. **观看端渲染性能**:30fps canvas blit 在 WebView 内可行;若卡顿,二期 WebCodecs 解决。

## 九、备选路线(记录,不推荐)

受控端跑 VNC server + websockify(WS→TCP 桥),控制端 Tauri 内嵌 noVNC 网页。优点:省掉自定义协议与编解码工作。缺点:与现有信任/协助流程整合度差(密码体系、一次性授权、反向协助都要绕 RFB 协议实现)、画质/延迟调优空间小、多一个前端依赖。仅作为快速验证的兜底方案。
